# 当“快”不再只是比较次数

## 这篇文档为什么单独开

在 `binary-search-unified-view.md` 里，我们主要讨论的是：

- 顺序
- 边界
- 信息增益
- 决策树
- 比较模型
- 下界

那一篇回答的核心问题是：

- **从信息和模型角度看，为什么二分重要，为什么某些复杂度不可能再低**

但工程里的“快”并不只由比较次数决定。

很多时候，更贵的是：

- cache miss
- 内存局部性差
- 指针跳转导致的乱访存
- 页访问次数
- 磁盘 / SSD I/O
- 写放大、读放大、合并成本

一旦讨论这些，主轴就变了。

所以这篇文档单独开，是为了把问题换成：

- **当成本模型从“比较次数”切到“访存 / 页 / I/O / 局部性”时，为什么结构设计会变？**

## 先把正文主线立起来：其实只有两个大问题

如果把这篇文档再压缩一层，会发现它真正围绕的只有两个问题：

- **怎么搜现有的数据**
- **怎么组织现有的数据**

这两个问题不是并列摆着的，它们其实互为表里。

因为：

- 你想怎么搜，决定了你希望一次操作拿到什么信息
- 你怎么组织，决定了这种信息能不能被便宜地拿到
- 查询模式反过来，又会逼着存储布局和索引结构改变

换句话说：

- 搜法是在定义“我希望一次访问值不值”
- 组织法是在定义“机器能不能低成本地把这种值钱访问实现出来”

所以这篇文档后面谈的局部性、页、B-Tree、LSM、排序，最好都放回这条主线上去看。

## 怎么搜：本质上是在设计一次访问要拿到多少信息

“怎么搜”看上去像算法问题，但在工程里它首先是个信息问题。

你可以有很多不同的搜法：

- 比较中点，排除一半
- 顺着树走一层，缩小一块范围
- 用哈希先把 key 打到小桶
- 用 Bloom Filter 先排除大量不可能
- 在页内做局部二分，在页间做目录导航

这些搜法真正不同的地方，不只是代码结构，而是：

- **一次访问到底希望获得什么信息**

例如：

- 二分想一次比较排掉半区
- 哈希想一步把候选压进极小局部
- Bloom Filter 想先廉价得到一个“肯定不在”的结论
- B+Tree 想一次页访问换来节点内多次局部判断

所以“怎么搜”不是一句泛话，而是在问：

- 我们到底希望单次访问达成哪种缩减未知空间的效果？

## 怎么组织：本质上是在决定这些信息能不能便宜地拿到

如果说“怎么搜”决定了信息目标，那么“怎么组织”决定的就是实现成本。

同样是想排掉一半、不想查太多页、想先做负筛选，不同组织方式会让代价完全不同。

例如：

- 连续数组让局部比较很便宜
- 指针树让动态更新容易，但追指针会贵
- B-Tree 把更多 key 压进一个页内节点，减少高代价页访问
- LSM 选择先顺序写再合并，换掉原地更新成本

所以组织方式真正回答的是：

- **为了支持某种搜法，我们愿意把数据排成什么样子？**

这就是为什么工程世界里，搜索和存储布局从来分不开。

## 互为表里：搜法在逼组织，组织也在反过来塑造搜法

这两者最有意思的地方在于，它们不是单向关系。

不是说先把数据随便摆好，再从里面挑一个搜索算法；也不是先随便想出一个搜索算法，再要求布局无条件配合。

更真实的过程往往是：

- 搜法提出一种理想的“单次信息获取方式”
- 组织法决定这种方式能否以低成本实现
- 一旦成本过高，搜法本身也会被改写

例如：

- 如果页访问很贵，就会倾向让一个节点更胖，从二叉走向多路
- 如果随机写很贵，就会把“原地维护有序”改成“先顺序写、后批量整理”
- 如果大量查询本该失败，就会把“直接搜”改成“先过滤再精查”

所以更准确的看法是：

- **搜索策略和数据组织是在共同演化的。**

这也是为什么这篇文档里，搜索结构、页布局、外存模型、排序工程可以放在一条主线上。

## 为什么它们不是先后独立决定，而是共同演化

这一步值得单独说清楚。

很多人直觉上会把问题拆成两步：

- 先决定用什么搜索策略
- 再决定把数据怎么存

或者反过来：

- 先把数据组织好
- 再在现有布局上挑一个搜索算法

但真实工程里，这两种理解都太静态了。

更常见的情况是：

- **搜索策略在逼组织方式改变**
- **组织方式又在反过来塑造可行的搜索策略**

它们不是流水线关系，而是来回塑形的关系。

## 查询模式会逼组织方式改变

如果系统主要做的是：

- 单点查找
- 范围扫描
- 高频更新
- 读多写少
- 大量失败查询

那这些查询模式本身就已经在对布局提出要求。

例如：

- 如果范围查询很多，数据通常就不能只按“等值查找最方便”的方式组织
- 如果写入很多，原地维护严格有序的代价就会被放大
- 如果大量请求都应该失败，前置过滤层就会变得很值
- 如果数据经常落外存，页级布局就会变成主导约束

也就是说，查询模式并不是在“使用既有数据布局”，而是在持续逼问：

- **这种布局还能不能支持我最常见、最贵的查询？**

一旦答案是否定的，布局就会被迫改变。

## 组织方式又会反过来塑造可用的搜索策略

反过来，一旦数据已经按某种方式组织起来，可行的搜索策略就会被它强烈限制。

例如：

- 连续数组天然鼓励二分和顺序扫描
- 页内节点天然鼓励“先定位页，再页内搜索”
- LSM 的多层有序段天然鼓励“先查元数据，再查段，再查块”
- Trie 的前缀结构天然鼓励按字符/bit 导航，而不是做整体比较

这说明什么？说明布局不是中性的容器。

它本身就在暗示：

- 哪些搜索动作便宜
- 哪些搜索动作昂贵
- 哪些搜索动作甚至已经不自然了

所以一旦组织方式定下来，搜索策略往往也随之被“重写”。

## 更真实的工程过程：不是选算法，而是在找平衡点

工程上更真实的过程通常是这样的：

- 先看到一类查询 / 更新模式
- 再尝试一种组织方式去支持它
- 然后发现某类访问成本过高
- 于是倒回来修改搜索路径、节点形状、页布局、索引层次

这个过程会反复发生，直到某个平衡点出现。

所以我们真正做的，不只是“选了一个算法”或“选了一个数据结构”，而是：

- **在查询模式、数据组织、硬件成本之间，反复逼近一个可接受的折中。**

这就是为什么：

- B-Tree 不是单纯的树
- LSM 不是单纯的有序文件
- 排序也不是单纯选一个 textbook 算法

它们全都是这种共同演化过程的产物。

## 一个更稳定的工程判断顺序

如果把这种“共同演化”翻成一个更稳定的判断顺序，可以这样想：

- 先看最主要的查询和更新模式是什么
- 再问一次访问最希望拿到什么信息
- 再问为了让这种访问便宜，数据必须组织成什么样
- 再反问这种组织方式会逼我接受哪些搜索路径、更新成本和维护代价
- 最后才比较不同方案在当前机器上的真实成本

这套顺序和“先挑算法、再挑数据结构”很不一样。

它更接近真实系统设计，因为它默认承认：

- 搜法和组织法从一开始就不是分开的。

## 为什么这一点会让后面的案例更容易看懂

把这层想清楚以后，后面的很多例子会一下子变得顺。

例如：

- B-Tree / B+Tree 不是“树的另一种写法”，而是在页代价下把搜索和布局一起改了
- LSM / SSTable 不是“放弃有序”，而是在写入成本面前重写了组织方式和读路径
- 排序工程不是“换个排序函数”，而是在输入分布、局部性、稳定性之间重写整套执行路径

所以这篇文档真正想立住的，不只是“工程里每一步更贵”，还包括：

- **一旦成本模型变了，搜索策略和数据组织就会一起变。**

## 先把问题说清：为什么同样是 `O(log n)`，工程表现会差很多

如果只看算法课上的复杂度表，很多结构都可能写成：

- 数组二分：`O(log n)`
- 平衡 BST：`O(log n)`
- 跳表：`O(log n)`
- B-Tree / B+Tree：`O(log n)`

但工程上它们常常完全不是一个量级。

原因不是复杂度错了，而是复杂度在这里只回答了一个很有限的问题：

- **需要多少步？**

而工程真正还要问的是：

- **每一步到底贵不贵？**

如果某一步只是做几次寄存器比较，那成本可能很低。
如果某一步意味着：

- 跨 cache line
- 追一次随机指针
- 触发一次 cache miss
- 读一页磁盘或 SSD block

那同样“一步”，代价可能已经完全不同。

所以这篇文档最核心的切换，就是把关注点从：

- **步数**

切到：

- **步数 × 单步代价**

## 比较次数之外，还要看什么成本

在工程里，常见的成本至少还有这些：

- **cache miss**：数据不在 L1 / L2 / LLC 里，要去更慢层级拿
- **内存局部性**：访问模式是否连续，是否容易被预取
- **指针跳转成本**：每次跳到未知地址，CPU 很难提前准备数据
- **页访问次数**：数据不在当前页里，就要多做一次页级访存或 I/O
- **磁盘 / SSD I/O**：随机读和顺序读代价差异很大
- **写放大 / 读放大 / 合并成本**：特别是在 LSM 一类结构里

所以工程里真正比较结构时，问题通常不是：

- 谁的渐近复杂度更漂亮

而是：

- 谁更符合机器的访存方式
- 谁能减少高代价层级上的访问次数
- 谁更适合当前读写比例和数据生命周期

## 局部性为什么会成为第一公民

现代机器快慢差异最大的地方，往往不是算术比较，而是数据离 CPU 有多远。

如果数据已经在 cache 里，做几次比较非常便宜。
如果数据散在内存各处，甚至不在内存里，那真正贵的是：

- 把数据搬到能比较的位置

这就让**局部性**变成了工程设计里的第一公民。

所谓局部性，最粗略地说，就是：

- 你下一步要用的数据，是否大概率就在刚才附近

局部性好的结构通常意味着：

- 连续访问多
- 预取容易生效
- cache line 利用率高
- 少做随机跳转

局部性差的结构通常意味着：

- 指针跟着指针跑
- 每一步都可能去完全不同的位置
- CPU 很难提前准备数据

所以从工程角度看，很多结构优化的目标都可以改写成一句话：

- **让下一步尽可能还在附近，而不是每次都重新去远处找数据。**

## 连续内存 vs 指针结构：为什么“同样是 log n”也会差很多

数组二分和树搜索，是最适合比较这个问题的一对。

数组二分的特点是：

- 数据连续存放
- 虽然访问下标不是线性的，但整体仍然建立在一块连续内存上
- cache、TLB、预取通常更友好

树结构的特点则是：

- 节点往往分散分配
- 每下一层就要追一次指针
- 下一跳地址在运行前不容易知道

于是即便两者都写作 `O(log n)`，单步成本也可能完全不同：

- 数组二分的每步常常是在较少的几个 cache line 之间跳
- 树搜索的每步可能都在触发新的 cache miss

这也是为什么工程上经常会看到一种现象：

- 对中等规模数据，排好序的数组 + 二分，可能比很多“理论上同级”的指针结构更快

原因不神秘，就是：

- **连续内存把每一步变便宜了**

## cache line 视角：机器读的不是一个元素，而是一整块

CPU 通常不是一次只取一个元素，而是按 cache line 取一块数据。

这意味着：

- 如果你的结构把相关数据放得很近
- 一次取数就可能把后面要用的内容也顺手带进来

这会让比较本身几乎变成顺带动作。

反过来，如果结构是大量零散节点：

- 每次真正贵的不是比较
- 而是为了比较，先要等数据到场

所以工程里常会看到这样一种价值排序：

- 少一次 cache miss，常常比少几次整数比较更值钱

这就是为什么很多数据结构设计看上去“多做了些比较”，却反而更快——
因为它们换来了更好的局部性。

## 页与块：外存环境下，成本模型再次变形

一旦数据规模大到经常不在内存里，问题就更明显了。

这时真正的昂贵动作变成：

- 读一个页
- 读一个 block
- 触发一次随机 I/O

于是外存环境里的核心目标会变成：

- **尽量减少需要读多少页**

这和纯比较模型已经不是一个重心。

在这里，一个结构是否“好”，往往首先看的是：

- 做一次查询要碰几个页
- 写一次更新要牵动多少页
- 范围扫描是否顺序友好

所以一旦切到外存模型，很多设计都会自然偏向：

- 更高扇出
- 更少层数
- 页内连续布局
- 顺序批量访问

## 一个过渡对照：数组、树、跳表在内存里各自像什么

可以把它们粗略看成三种不同的工程气质。

### 排序数组 + 二分

优点：

- 连续内存友好
- 查找常数小
- 范围扫描自然

代价：

- 动态插入删除代价高

适合：

- 静态或读多写少的数据

### 平衡树 / 指针树

优点：

- 动态更新自然
- 有序语义完整

代价：

- 指针跳转多
- 局部性通常较差

适合：

- 动态有序集合
- 需要前驱/后继/范围等顺序操作

### 跳表

优点：

- 动态性较好
- 实现思路相对直观
- 分层索引思想清楚

代价：

- 仍然有较多指针访问
- 局部性通常不如连续数组页内结构

适合：

- 需要动态更新
- 又希望结构逻辑清晰、实现和并发设计相对友好

这里没有谁“绝对更先进”，只有：

- 在什么读写比例
- 什么内存层次
- 什么更新模式
- 什么实现复杂度约束

下，谁更合适。

## 三个案例：当成本模型变化时，结构为什么会一起变

前面的主线和成本模型现在已经立住了。接下来不再平铺概念，而是看三个更像“共同演化结果”的案例：

- **B-Tree / B+Tree**：页代价很高时，搜索路径和节点布局如何一起变化
- **LSM / SSTable**：写入成本很高时，组织方式和读路径如何一起变化
- **排序工程**：输入分布、局部性、稳定性约束如何一起重写执行路径

这三个案例长相不同，但回答的是同一个问题：

- **当高代价动作变了，搜索策略和数据组织会怎样一起改写？**

## 案例一：B-Tree / B+Tree 是页代价下的共同演化结果

B-Tree / B+Tree 的外形，并不是因为发明者喜欢复杂节点，而是因为它们在页模型下很自然。

如果一页能装很多 key，那么一个节点就不必只做一次二选一决策，而可以做：

- 一次页访问
- 页内再做多路选择

这样做的好处是：

- 把许多原本分散在多层树节点里的信息，压进同一个页里
- 让一次昂贵页访问，换来更多局部决策能力

这就是 B-Tree / B+Tree 的核心工程直觉：

- **宁愿把一个节点做胖，也要减少树高和页访问次数**

而 B+Tree 更进一步：

- 内部节点主要负责导航
- 数据集中放在叶子
- 叶子之间通常还能顺序链接

这样一来：

- 单点查找路径清楚
- 范围扫描也更自然

所以 B+Tree 在数据库和文件系统里很常见，不是偶然，而是因为它同时照顾了：

- 查找
- 范围遍历
- 页局部性

如果把它再压得更清楚一点，可以这样看：

- **它要解决的主要矛盾**：页访问太贵，不能再让树高和随机页跳转失控
- **它改写的搜索路径**：从“频繁跨页做细碎判断”改成“先进一个更胖的节点，再在页内做更多局部判断”
- **它重塑的组织方式**：把更多 key 和路由信息压进页内节点，用更高扇出换更少层数

### 为什么页代价下宁愿多比较，也要少 miss 和 I/O

到这里就能看明白一个很常见的工程现象：

- 有些结构明明比较次数更多，却反而更快

原因通常不是比较被神奇优化了，而是：

- 这些比较发生在已经加载进来的连续数据里
- 代价低于一次新的随机访存或页访问

所以工程上常见的真实取舍不是：

- 少比较 vs 多比较

而是：

- 多做几次便宜比较，能不能换掉一次昂贵 miss / I/O

如果能，那往往是值得的。

这也是为什么：

- 页内二分
- cache-friendly layout
- node packing
- 批量顺序访问

这些技巧会反复出现。

## 案例二：LSM / SSTable 是写入成本下的共同演化结果

LSM 这条线关心的重点又不一样。

它不是先问“单次点查最低多少层”，而是先问：

- **写入能不能足够便宜？**

如果写很多，而每次都原地改页、维持严格有序，代价会很高。

于是 LSM 的思路变成：

- 先顺序写
- 后续再批量整理和合并

SSTable / segment file 这一层通常提供的是：

- 文件内部局部有序
- 可做稀疏索引
- 可做块级查找
- 顺序扫描友好

所以它不是在否定 B-Tree，而是在不同成本模型下换了目标函数：

- **用更复杂的读路径和后台合并，换更便宜的写路径与顺序 I/O**

于是你会看到一整套新的工程词汇：

- 写放大
- 读放大
- compaction
- leveled / tiered

这些都说明：

- 在 LSM 世界里，“快”不只是一次查找少几步，而是整个读写系统的总成本更优

如果把它也压成同样的三句话，就是：

- **它要解决的主要矛盾**：写入太贵，不能每次更新都去原地维护严格有序布局
- **它改写的搜索路径**：从“直接在单一有序结构里查”改成“先查元数据，再查层级，再查段和块”
- **它重塑的组织方式**：把数据改成可顺序写、可批量合并的多层有序段，而不是始终维持一棵原地更新的单体结构

## 案例三：排序工程是输入分布与机器成本下的共同演化结果

你刚才提到排序，这个提醒很重要。

因为一旦我们接受了这篇文档的主线：

- **快不只是步数，还要看单步代价**

那么排序就会立刻变成一个非常强的例子。

表面上看，很多排序都会被归到相近的复杂度层级里：

- 快速排序：平均 `n log n`
- 归并排序：`n log n`
- 堆排序：`n log n`
- TimSort：最坏也在 `n log n` 级别
- 基数排序：在特定 key 模型下甚至不走比较排序那条线

但工程上它们的差异往往非常大。

原因和前面讨论搜索结构时是同一类：

- 数据是不是连续访问
- 分支是否容易预测
- 内存访问是否规律
- 是否需要额外缓冲区
- 写入模式是否友好
- key 的表示能不能被批量处理或 SIMD 化
- 数据分布是否能被算法利用

所以排序的工程深度，确实一点也不浅。它不是“同一个 `n log n` 里挑一个实现”，而是：

- **在不同成本模型、数据分布和稳定性约束下，选择不同的排序路线。**

如果也用同一个框架来压缩它，就是：

- **它要解决的主要矛盾**：不是单纯把元素排好，而是在局部性、稳定性、原地性、分支行为之间找平衡
- **它改写的搜索路径**：这里的“搜索路径”变成了元素比较、分区、归并、分发这些执行路径本身如何组织
- **它重塑的组织方式**：不是只换一个排序函数，而是随着输入分布、key 结构和机器成本，重写数据移动与访问模式

### 为什么快排、堆排、归并哪怕同阶，也完全不是一个味道

先看几个最典型的对比。

### 快速排序

工程上很多场景里，快排很强，常见原因包括：

- 分区操作往往落在连续内存上
- 局部性通常不错
- 常数因子往往比较小
- 原地性质常常很有吸引力

但它的代价也清楚：

- 最坏情况不理想
- 分支行为和 pivot 质量会影响很大
- 对某些分布很敏感，需要工程化防护（例如 introsort 一类思路）

### 堆排序

堆排序的理论形状很漂亮：

- 最坏 `n log n`
- 原地

但工程上它常常没有那么受欢迎，原因就在于：

- 堆的访问模式更跳跃
- cache 局部性通常不如快排和归并
- 单步的访存行为没有那么顺滑

所以堆排序常常像是：

- 理论保证很硬
- 但机器执行起来不够“顺手”

### 归并排序

归并排序的一个大优点是访问模式非常规整：

- 顺序读
- 顺序写
- 容易形成流式访问

所以在很多内存层次和外存场景里，它的工程气质非常好。

但代价也明显：

- 常常需要额外缓冲区
- 原地性不如快排 / 堆排自然

所以归并排序常常体现的是一种工程交换：

- **用额外空间，换取更规整、更可预测的访存行为**

### 稳定性、原地性、局部性：工程里常常不是同一个目标

一旦进入工程世界，排序就不只是问：

- 渐近复杂度是多少

还要问：

- 稳定吗？
- 原地吗？
- 顺序访问友好吗？
- 额外空间大吗？
- 对 branch predictor 友好吗？
- 对 cache / SIMD / 并行友好吗？

这些目标有时彼此冲突。

例如：

- 更稳定的算法，可能需要更多额外空间
- 更原地的算法，可能牺牲访问规律性
- 访存最规整的算法，未必比较次数最少

所以排序的工程世界其实和前面搜索结构的世界非常像：

- **你不是只在选一个复杂度，而是在选一组成本交换关系。**

### 基数排序为什么又是另一种世界

基数排序之所以值得单独提，是因为它再次说明：

- 一旦你换了模型，复杂度图景就会变

基数排序不依赖元素之间的比较顺序，而是：

- 利用 key 的位或字符表示
- 按位 / 按 digit 分发

所以它和哈希、Trie 在某种意义上是同一类提醒：

- **别把“比较模型里的下界”误当成所有模型里的天花板。**

但基数排序也不是白赚的，它的前提包括：

- key 类型可被分解成 digit / byte / bit
- digit 数量和桶管理成本是可接受的
- 额外空间、写回模式、稳定性实现都要纳入成本

所以基数排序工程上强不强，不只取决于理论复杂度，还取决于：

- key 长度
- key 分布
- cache 行为
- 写放大
- 桶结构是否友好

它再次证明了一件事：

- **工程里“快”从来不是单一维度。**

### TimSort 这种工程算法为什么会出现

TimSort 这类排序的存在，本身就说明排序已经进入很深的工程区。

它不是单纯站队某一种 textbook 算法，而是试图利用：

- 输入中本来就存在的局部有序性
- 稳定排序需求
- 归并类算法的规律访存

这类算法在工程上有吸引力，是因为它不只是问：

- 最坏情况下理论怎样

它还问：

- 真实数据通常长什么样
- 输入是不是已经部分有序
- 系统更希望稳定性、局部性还是原地性

所以这类排序算法体现的是另一种成熟工程思路：

- **不是只优化抽象输入，而是优化真实工作负载。**

### 为什么排序正是这条主线的典型练兵场

搜索结构和排序算法表面上是两类主题，但进入工程深处后，它们在问非常相似的问题：

- 连续内存还是指针跳转？
- 少几次比较，值不值一次 cache miss？
- 额外空间能不能换更规整的访存？
- 稳定性、原地性、并发性、SIMD 友好性谁更重要？
- 工作负载是静态、动态、随机、局部有序，还是批处理？

所以你说“排序上了数量级之后工程深度也很深”，这个判断是对的。

它甚至可以单独再展开成一篇文档，但在当前这篇里，至少应该明确这件事：

- **排序不是工程成本模型之外的例外，排序正是这个模型最典型的练兵场之一。**

## 如何把“理论最优”翻译成“工程上更快”

可以把这件事压成几个工程判断：

- 如果数据大多驻留 cache / 内存，局部性会非常重要
- 如果数据常常落到外存，页访问次数会比比较次数更重要
- 如果写入很多，更新路径和后台整理成本要进入主导地位
- 如果读多写少，重预处理和压缩布局可能很值
- 如果范围扫描很多，保序和顺序访问会非常重要

所以真正成熟的工程判断通常不是：

- “这个结构理论复杂度最低，所以应该用它”

而是：

- **在当前机器和当前工作负载下，哪个结构让高代价动作最少发生。**

### 给后续接手者的实验设计指北

- 先按这篇文档的主线拆实验，而不是按结构名堆实验：
  - 一组实验回答“怎么搜现有的数据”
  - 一组实验回答“怎么组织现有的数据”
  - 一组实验回答“搜索策略和组织方式如何共同变化”

- 先固定问题，再换结构；不要一上来横向堆很多实现：
  - 点查
  - 范围查
  - 读多写少
  - 写多读少
  - 静态集合
  - 高频更新集合

- 指标不要只看吞吐和时延，要同时记录高代价动作：
  - cache miss
  - branch miss
  - 页访问 / I/O 次数
  - 内存带宽
  - 额外分配与写回模式

- 数据分布要故意做分层，不要只测随机均匀数据：
  - 随机
  - 近乎有序
  - 逆序
  - 重复值很多
  - 局部热点明显

- 搜索结构优先可做的对照组：
  - 排序数组二分 vs BST / 跳表 / B-Tree 风格节点布局
  - 不同数据规模跨 L1 / L2 / LLC / DRAM / 磁盘的转折点
  - B-Tree node size / page size / fanout 的影响
  - LSM compaction 策略、读放大、写放大的对照

- 排序结构优先可做的对照组：
  - 快排 / 堆排 / 归并 / TimSort / 基数排序
  - 比较稳定性、原地性、SIMD 友好性、并行化潜力对选型的影响
  - 单独梳理“比较排序下界成立，但基数排序为何能换模型绕开它”的说明与数据

- 最后再决定脚本长什么样，而不是先写脚本再找问题。
